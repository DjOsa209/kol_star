# IP 需求反馈时效

## 业务规则

- 需求正式提交，记录 `submitted_at`，从次日开始计算 **10 个工作日**，作为 IP 意见最晚反馈时间。
- IP 组完成所有意向 IP 的必填评估并正式提交，记录 `ip_reviewed_at`，从次日开始计算 **5 个工作日**，作为营销意见最晚反馈时间。
- IMC、品牌运营、用户运营、媒介投放、PR 五个职能分别填写、保存草稿和提交。只有五个职能都正式提交后，才记录 `marketing_reviewed_at` 并通过飞书应用消息提醒需求发起人，消息链接进入原需求详情。
- 草稿不启动下一阶段、不重置当前期限、不触发完成提醒。所有营销职能共用 IP 意见提交后 5 个工作日的期限，各伙伴提交不会重置期限。逾期仍允许补交，并显示逾期提交状态。
- 按中国大陆法定放假和调休，统一北京时间 `Asia/Shanghai`。截止日全天有效，存储的截止时间为 `23:59:59+08:00`，界面显示 `23:59`。
- 列表展示对应环节的截止时间、剩余工作日、今日截止、逾期或已完成状态；详情同时展示两个环节。剩余工作日不含今天，逾期工作日从截止日次日起统计，含当前工作日。
- 旧需求的开始时间无法从 `created_at`（可能是草稿创建）或 `updated_at`（可能是编辑/保存草稿）可靠恢复。因此迁移保留 NULL，显示时间缺失，避免错误追责；旧需求下一次正式流转会记录之后的真实时间。

## 分职能协作与飞书提醒

伙伴在现有“营销意见补充”菜单中选择其负责的职能，独立填写和提交。本次提交只校验、更新所选职能，不要求填写其他伙伴的意见。继续沿用营销菜单权限，不额外引入按对接人 ID 强绑定的新访问规则。页面展示各职能已提交/待提交及总进度。

| 职能 | 本职能分 IP 必填项 | 其他内容 |
| --- | --- | --- |
| IMC | IP热度、粉丝受众、商业价值、短板与风险、近一年趋势、社媒粉丝总数 | 品牌调性价值和项目整体判断选填 |
| 品牌运营 | 用户内容预测 | — |
| 用户运营 | 受众匹配 | — |
| 媒介投放 | 无强制 CPM 数值 | CPM 选填，不强迫编造无法确认的数值 |
| PR | 舆情判断 | — |

每个职能正式提交时需要填写**本职能的补充意见**，推荐传播方向选填；草稿允许不完整。所有必填星号统一显示红色，并与字段名同行。已提交职能为只读，其余职能仍可继续填写。

意见合并保存在原 `marketing_profile` JSON 中：`candidates` 继续使用已有各 IP 的扁平字段，兼容查看与导出；`functions.<职能>` 保存版本、补充意见、传播方向、提交人/时间、最后修改人/时间。接口要求 `functionKey` 和本职能 `version`，只接受该职能字段；在需求行锁内读取最新 JSON 并局部合并，不使用旧页面的整个快照覆盖数据库。不同职能并发可分别成功；同职能旧版本和重复提交返回 409。正式提交某职能不会清空或重置其他职能。

旧的已完成需求保持完成；旧的共享草稿、分 IP 字段和补充意见继续保留，历史补充意见单独展示，不会虚构五个职能都已提交。新协作流程以五个明确的职能提交记录为完成依据。

提醒沿用现有**飞书应用消息**：需求提交通知 IP 对接人；IP 意见提交通知五个营销职能对接人，均包含反馈周期与最晚反馈时间；第五个职能正式提交、事务成功后，仅通知需求 `created_by` 发起人，不能用可编辑的负责人文本或产品对接人代替。前四个职能、保存草稿、失败或重复提交不触发完成通知。上一版新增的站内弹窗、需求消息标签、轮询和写入均已移除。迁移 054 已创建的旧站内通知表保留，不删除历史数据。

飞书需沿用现有启用状态、应用凭据及可解析的接收人邮箱；发送失败会记日志，不回滚已成功保存的意见。此通道未实现失败重试队列，不把数据库提交成功等同于飞书实际送达。测试使用注入的模拟发送器或禁用真实飞书，不给同事发送测试消息。

## 年度日历与维护

内置年度数据：`backend/cmd/server/data/cn_work_calendar.json`，包含已核验的 **2025、2026** 全年假期区间及补班日期。

核验来源：

- [国务院办公厅关于2025年部分节假日安排的通知（国家林草局转载）](https://www.forestry.gov.cn/c/www/szxx/594663.jhtml)
- [国务院办公厅关于2026年部分节假日安排的通知](https://www.gov.cn/zhengce/content/202511/content_7047090.htm)，[北京市政府转载](https://www.beijing.gov.cn/cs/gncs/zcwj/202603/t20260327_4568275.html)

后续年度应在国务院发布完整年度安排后，核验所有节假日与周末补班，将完整年度条目加入 `config.yaml` 的 `work_calendar` 列表。配置热更新生效，无需改代码；也可在发布版本中更新内置 JSON。每个条目包含：

| 字段 | 内容 |
| --- | --- |
| `year` | 已核验的年份 |
| `source` | 官方安排的 HTTPS 核验链接 |
| `holidays` | 全年放假区间字符串列表，格式 `YYYY-MM-DD/YYYY-MM-DD`，首尾均包含；一天假期的起止相同 |
| `workdays` | 全年周末补班日期字符串列表，格式 `YYYY-MM-DD` |

同年配置**替换完整年度**，不能只补其中一个假日。校验重复年份、非法日期、跨年日期、重叠区间、假期与补班冲突；无效配置不生效。日历不能单靠农历或周一到周五算法推算，因为每年的调休安排不同。

缺少任何计算所需年度时，需求仍可提交并保留真实阶段开始时间，界面明确显示“年度日历待核定”，不虚构截止日期。补入该年配置后自动恢复计算。已知截止日期仍可判断是否逾期；若统计剩余/逾期工作日所需后续年度缺失，会同时显示日历警示。该实现不包含自动抓取或未经核验的年度预测，运维需按年维护配置。
