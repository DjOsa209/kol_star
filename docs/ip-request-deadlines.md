# IP 需求反馈时效

## 业务规则

- 需求正式提交，记录 `submitted_at`，从次日开始计算 **10 个工作日**，作为 IP 意见最晚反馈时间。
- IP 组完成所有意向 IP 的必填评估并正式提交，记录 `ip_reviewed_at`，从次日开始计算 **5 个工作日**，作为营销意见最晚反馈时间。
- 营销组填齐所有意向 IP 的必填意见并正式提交，记录 `marketing_reviewed_at`，发起人收到站内完成通知和弹窗，可直接进入原需求详情。
- 草稿不启动下一阶段、不重置当前期限、不触发完成提醒。逾期仍允许补交，并显示逾期提交状态。
- 按中国大陆法定放假和调休，统一北京时间 `Asia/Shanghai`。截止日全天有效，存储的截止时间为 `23:59:59+08:00`，界面显示 `23:59`。
- 列表展示对应环节的截止时间、剩余工作日、今日截止、逾期或已完成状态；详情同时展示两个环节。剩余工作日不含今天，逾期工作日从截止日次日起统计，含当前工作日。
- 旧需求的开始时间无法从 `created_at`（可能是草稿创建）或 `updated_at`（可能是编辑/保存草稿）可靠恢复。因此迁移保留 NULL，显示时间缺失，避免错误追责；旧需求下一次正式流转会记录之后的真实时间。

## 通知

阶段推进时，通知与状态更新在同一数据库事务中写入。`(request_id,user_id,stage)` 唯一键配合阶段行锁，防止并发提交产生重复完成通知。营销角色重复指向同一同事时，只产生一条站内提醒。

顶部“消息提醒 → IP需求”展示本人待办及已完成提醒。待办含最晚反馈的日期；已完成阶段的过期待办不再展示。完整意见只向需求 `created_by` 发起人弹窗，不能用可编辑的项目负责人文本替代。关闭或点击查看会持久化已读，刷新不再弹出。站内提醒在登录后、窗口重新激活时检查，打开期间每 60 秒检查；发起人离线期间的未读提醒会保留到下次登录。

现有飞书阶段消息继续按原配置发送，新增反馈周期和具体截止时间。只有开启原有飞书应用配置且联系人可解析时才会发送；自动测试禁用此通道，不给真实同事发消息。站内通知只允许本人读取和确认。

## 年度日历与维护

内置年度数据：`backend/cmd/server/data/cn_work_calendar.json`，包含已核验的 **2025、2026** 全年假期区间及补班日期。

核验来源：

- [国务院办公厅关于2025年部分节假日安排的通知（国家林草局转载）](https://www.forestry.gov.cn/c/www/szxx/594663.jhtml)
- [国务院办公厅关于2026年部分节假日安排的通知](https://www.gov.cn/zhengce/content/202511/content_7047090.htm)，[北京市政府转载](https://www.beijing.gov.cn/cs/gncs/zcwj/202603/t20260327_4568275.html)

后续年度应在国务院发布完整年度安排后，核验所有节假日与周末补班，将完整年度条目加入 `config.yaml` 的 `work_calendar` 列表。配置热更新生效，无需改代码；也可在发布版本中更新内置 JSON。每个条目包含：

| 字段 | 内容 |
| --- | --- |
| `year` | 已核验的年份 |
| `source` | 官方安排的 HTTPS 核验链接 |
| `holidays` | 全年放假区间字符串列表，格式 `YYYY-MM-DD/YYYY-MM-DD`，首尾均包含；一天假期的起止相同 |
| `workdays` | 全年周末补班日期字符串列表，格式 `YYYY-MM-DD` |

同年配置**替换完整年度**，不能只补其中一个假日。校验重复年份、非法日期、跨年日期、重叠区间、假期与补班冲突；无效配置不生效。日历不能单靠农历或周一到周五算法推算，因为每年的调休安排不同。

缺少任何计算所需年度时，需求仍可提交并保留真实阶段开始时间，界面明确显示“年度日历待核定”，不虚构截止日期。补入该年配置后自动恢复计算。已知截止日期仍可判断是否逾期；若统计剩余/逾期工作日所需后续年度缺失，会同时显示日历警示。该实现不包含自动抓取或未经核验的年度预测，运维需按年维护配置。
